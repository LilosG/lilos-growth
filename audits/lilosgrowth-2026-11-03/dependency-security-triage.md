## Priority categories

### Critical (runtime dependency audit)

- `fast-xml-parser`: vulnerable XML entity/DoS behaviors across several advisories. Audit reports a compatible fix **available**, but direct parent chain and resulting lockfile need to be inspected before updating.
- `tar`: archive extraction and decompression issues, including DoS and path traversal. Audit reports a compatible fix **available**. Determine whether this is only build/install usage or part of any deployed function.

### High (runtime dependency audit)

- Direct: `@astrojs/sitemap` (compatible fix reported), `astro-icon` (compatible fix reported), `@astrojs/vercel` (**major migration required**, audit recommends 11.0.18), `astro-embed` (**major migration required**, audit recommends 0.14.0), `zod` (**major migration required**, audit recommends 4.6.7).
- Transitive: `@vercel/routing-utils`, `path-to-regexp` (associated with adapter migration), `@atproto/*` and `@astro-community/astro-embed-*` (associated with embed migration), plus `@iconify/tools`, `brace-expansion`, `extract-zip`, `minimatch`, `picomatch`, `source-map-js`, `svgo`, `undici` (compatible fixes reported for these packages). Resolve transitive versions using a lockfile-aware installer; do not edit nested lockfile entries by hand.

### Development-side critical

- `astro`: audit recommends Astro 7.4.5 (major migration from the working Astro 5 stack), including security advisories. Plan with `@astrojs/vercel`, `@astrojs/mdx` and affected integrations.
- `tinypool` / `vitest`: audit recommends Vitest 5.1.0, a major change from Vitest 2.

## Remediation sequence

1. **Compatible, lockfile-resolved changes first:** use `npm audit fix --package-lock-only` *without* `--force` on a dedicated security branch, review `npm audit --json` before/after, check `package.json` and all nested version changes, then `npm ci`, `npm run check:astro`, `npm run check:eslint`, `npm run check:ts`, `npx vitest run`, `npm run build`, and Vercel preview. Limit package upgrades to semver-compatible patches where possible. Lockfile changes must be generated by npm, never guessed.
2. **Astro platform migration:** in a separate branch, upgrade Astro, adapter, MDX and compatible integrations together; handle breaking APIs, TypeScript, static routes, RSS/sitemap, canonicals, redirects and tests. Validate user-facing pages and runtime behavior before release.
3. **Other majors in distinct compatibility batches:** `astro-embed`, `zod`, `vitest`/test tools, and any required Sharp/toolchain upgrade. Avoid mixing Tailwind 3→4 or TypeScript 5→7 with the security migration unless proven necessary.
4. **Risk review:** determine whether XML parsing, archive extraction, rendering or user-controlled values reach exposed server endpoints. Prioritize based on actual reachability and available fixes, not only an audit count. Preserve Node 22 and existing passing production deployment until tested changes are ready.

## Guardrails

- Never use `npm audit fix --force` to bypass major-version constraints.
- No mass automatic lockfile overwrite on `main`.
- Never label 58 audit findings as 58 directly exploitable production vulnerabilities.
- A passing Vercel build alone is insufficient: use the GitHub check and build jobs plus browser/route QA.
- This document does **not** claim vulnerabilities have been remediated. It is an evidence-based triage and implementation plan.
